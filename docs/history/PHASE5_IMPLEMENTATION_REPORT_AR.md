# تقرير تنفيذ المرحلة الخامسة
## CampusPass IQ V6.9 — Operations, Hosting & Updates

## الهدف
تحويل البوت من مشروع يعمل عند توفر الظروف إلى خدمة يمكن تشغيلها وتحديثها ونقلها واستعادتها بواسطة مالك غير مبرمج، مع عدم فقدان قاعدة البيانات أو تكرار المهام بعد إعادة التشغيل.

## ما تم تنفيذه

### 1. سجل نشر دائم
أضيف جدول `cp_deployment_releases` ويسجل كل مكوّن تشغيل بصورة مستقلة، حتى لا تكتب خدمة bot فوق حالة worker أو العكس:
- `RELEASE_ID` والإصدار والبيئة، مع التقاط `RAILWAY_DEPLOYMENT_ID` وGit SHA تلقائياً على Railway.
- وضع التشغيل `combined/bot/worker`.
- Git SHA والإصدار السابق.
- آخر Migration.
- بدء النشر ووقت الجاهزية والفشل والتوقف.

### 2. أوضاع تشغيل قابلة للفصل
- `combined`: API + Telegram polling + worker.
- `bot`: API + Telegram polling فقط.
- `worker`: API health + المهام الخلفية فقط.

هذا يسمح بالبداية على خدمة واحدة، ثم فصل العامل عند زيادة الحمل دون تغيير قاعدة البيانات.

### 3. Readiness حقيقي
`/health/ready` لم يعد يعتمد على فتح المنفذ فقط. يتحقق من:
- اتصال قاعدة البيانات.
- تسجيل الإصدار.
- جاهزية البوت إذا كان مطلوباً.
- جاهزية العامل إذا كان مطلوباً.

### 4. مهام مجدولة دائمة وغير مكررة
أضيف `cp_scheduled_runs` مع unique key وlease. أصبح:
- التقرير اليومي يعمل إذا تجاوز السيرفر الدقيقة المحددة.
- دورة الاشتراكات والخصوصية لا تتكرر في الساعة نفسها.
- النسخ الاحتياطي لا يتكرر بعد Restart.
- المهام الفاشلة تسجل وتُعاد بعد انتهاء lease.

### 5. نسخ احتياطي PostgreSQL مشفر ومتحقق
- استخدام `pg_dump` بصيغة custom مضغوطة.
- كلمة مرور قاعدة البيانات تمر عبر `PGPASSWORD` ولا توضع في arguments.
- تشفير الملف قبل الرفع.
- رفع إلى S3/R2/MinIO.
- تنزيل النسخة بعد الرفع وفكها ومقارنة SHA-256.
- سجل `cp_backup_runs` للحالة والحجم والبصمة ومدة الاحتفاظ.
- حذف النسخ المنتهية وفق السياسة.

### 6. نسخة قبل تحديث قاعدة البيانات
عند وجود Migration جديدة، يستطيع النظام إنشاء نسخة محققة قبل تنفيذها. يمكن جعلها إلزامية بواسطة:
`REQUIRE_PRE_DEPLOY_BACKUP=true`.

### 7. استعادة خارجية آمنة
أضيف `ops/restore_backup.py` ولا يعمل إلا مع تأكيد صريح:
`--confirm RESTORE-CAMPUSPASS`.
ويتحقق من SHA-256 قبل `pg_restore`.

### 8. سجل أعطال مركزي
أضيف `cp_runtime_incidents`:
- رمز ثابت للعطل.
- المصدر والخطورة والتفاصيل.
- عدد مرات التكرار.
- فتح/إقرار/إغلاق.

يسجل العامل مثلاً `SCH-MAIN`، والنسخ الاحتياطي `BKP-LATEST`.

### 9. تدوير مفاتيح التشفير
- `MultiFernet` لقراءة المفتاح الحالي والقديم.
- المفتاح الجديد في `ENCRYPTION_KEY`.
- القديم في `ENCRYPTION_KEYRING`.
- زيادة `ENCRYPTION_KEY_VERSION`.
- تدوير تدريجي للملفات الشخصية والطلبات والأدلة.
- لا يزال حذف المفتاح القديم ممنوعاً قبل انتهاء جميع الدفعات.

### 10. حماية Staging
عند `ENVIRONMENT=staging` يرفض النظام استخدام نفس Bot Token الخاص بالإنتاج بالاعتماد على بصمة SHA-256، حتى لا تسحب بيئة الاختبار تحديثات المستخدمين الحقيقيين.

### 11. أوامر المالك
- `/deployment_status`
- `/backup_status`
- `/run_backup`
- `/rotate_keys`
- `/resolve_incident CODE`
- `/diagnostics`
- `/recent_errors`

### 12. أدوات التشغيل
- `ops/preflight.py`
- `ops/backup_now.py`
- `ops/restore_backup.py`

## ما لم يتم ادعاء اختباره حياً
- حساب S3/R2 حقيقي.
- `pg_dump` ضد قاعدة Neon الحقيقية.
- Restore إلى PostgreSQL حقيقي.
- فصل خدمة bot عن worker على مشروع Railway حقيقي.
- مراقب خارجي مثل Sentry/UptimeRobot؛ تمت تهيئة نقاط health والسجل الداخلي، والربط الخارجي يدخل ضمن Pilot.

## القرار
V6.9 جاهزة لـStaging ولبدء Phase 6. لا تعتبر النسخ الاحتياطية صالحة قبل نجاح أول `/run_backup` ثم تجربة Restore على قاعدة منفصلة.
