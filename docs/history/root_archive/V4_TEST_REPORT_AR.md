## رحلة الشراء المختبرة

تم إنشاء بيئة مستقلة ومحاكاة:

```text
منصة
→ قسم أدوات الذكاء الاصطناعي
→ خدمة Gemini
→ عرض 30 يومًا
→ حساب مشفر في المخزون
→ طالب
→ إنشاء طلب وحجز المورد
→ اختيار طريقة دفع المنصة
→ رفع الإثبات
→ قبول موظف المنصة
→ تثبيت الحجز
→ إنشاء Delivery Job
→ إرسال البيانات
→ إنشاء اشتراك الطالب والوصل
→ تأكيد التفعيل
→ إكمال الطلب وإنشاء Ledger
```

التحقق شمل:

- عدم ظهور سر IMAP المخزن داخل JSON للطالب.
- المورد نفسه لا يبقى Available بعد التسليم.
- الاشتراك يأخذ بداية ونهاية صحيحتين.
- الوصل يحفظ اسم المنصة والسعر والتاريخ.
- القيود المالية والنقاط تُنشأ بعد الإكمال.

## اختبارات الصلاحية

- 30 يومًا ليست مساوية دائمًا لشهر تقويمي.
- 31/01 + شهر يعالج نهاية فبراير بصورة صحيحة.
- التاريخ الثابت.
- تاريخ المورد الموجود في المخزون.
- المدة اليدوية.
- رفض بيع عرض ثابت انتهى أو بقي أقل من الحد الأدنى.

## اختبارات الحماية

- منع وسيلة دفع تابعة لمنصة أخرى.
- منع تكرار مرجع الدفع بين الطلبات.
- Unique Constraint لبصمة الحساب أو الكود.
- منع تسريب أسرار صندوق البريد ضمن تسليم الحساب.
- Workflow يرفض القفز من انتظار الدفع إلى مكتمل.
- تعريف Workflow القديم يُحدّث إلى الإصدار الحالي.
- الموظف يرى ويدير بيانات منصته ضمن العلاقات المخصصة.

## اختبارات تجربة الاستخدام

- Reply Keyboard وInline Keyboard والوضع المختلط.
- جميع Callback Data ضمن حد Telegram البالغ 64 بايت.
- الأزرار الجديدة للمنصة موجودة.
- رسالة المعالجة تظهر فقط عندما تتجاوز العملية المهلة.
- رسالة المعالجة تُحذف بعد النجاح.
- الخطأ غير المتوقع يعطي رقم متابعة.
- Rate Limit يجيب Callback ولا يترك Spinner عالقًا.

## ما لم يُختبر من هذه البيئة

- Bot Token الحقيقي وحساب Telegram الحي للمستخدم.
- PostgreSQL Railway الفعلي تحت ضغط متزامن.
- Gmail/Yahoo/IMAP حقيقي؛ الاختبارات غطت المنطق والعزل فقط.
- بوابة Mastercard حقيقية.
- استعادة Backup حقيقية من مشروع Railway الخاص بالمستخدم.

لذلك التصنيف المناسب هو: **جاهز لنشر تجريبي مغلق، ثم اختبار طلب منخفض القيمة قبل الإطلاق العام**.
